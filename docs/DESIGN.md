> 中小企業診断士 2次試験「事例Ⅳ」＋ 1次「財務・会計」の基礎を、**明るいラボで検証を重ねるように**鍛える学習アプリ。

> - アプリ名：Rondo F&A（ロンド。同じ主題が何度も巡る曲。毎日くり返す学習になぞらえた。ロゴ・アイコンは `public/brand/`）
>
> - 作成日：2026-10-01
> - ステータス：実装中（ブランチ `v2/foundation`）。学習コース・レベル・認定・復習の詳しい設計は [`docs/COURSE.md`](COURSE.md)

## 1. 目的とゴール

### 目的
事例Ⅳで安定して得点できる計算力と判断力を、毎日の短い演習で身につける。

### v1 からの方針転換
| | v1（現行） | v2 |
|---|---|---|
| 学習の中心 | 自由に仕訳を入力し、財務諸表の変化を眺める | **問題を解き、自動で採点される** |
| クエスト | 自己申告でクリア（答え合わせなし） | 計算エンジンが正解を出して採点 |
| 範囲 | 仕訳 → 財務諸表 → 経営分析・CF | 仕訳ラボ＋経営分析・CF・CVP・NPV（順次拡張） |
| 世界観 | ダーク、ファンタジー（預言・精霊） | **明るく、シンプルでスタイリッシュなラボ** |
| 技術 | ブラウザ内の Babel、CDN の Tailwind、型とテストなし | Vite + TypeScript、テスト付きの計算エンジン |

### ゴール（この版で達成すること）
1. 論点 0〜4 の問題を、数値を変えながら何度でも解ける
2. 解答はその場で採点され、間違えた原因まで返ってくる
3. 学習コース（単元の定着とコースレベル）・認定・ストリークで、上達と継続が目に見える
4. PC とスマホのどちらでも快適に使える

### 当面やらないこと
- v1 のデータの引き継ぎ（ブラウザに保存された仕訳やストーリーは移行しない）
- ログイン（端末間の同期はログインなしの「同期キー」で行う。§9.3）
- 他ユーザーとの共有やランキング（公開は本人の合格後に検討）
- 記述問題の本格的な自動採点（当面はキーワードが入っているかで目安の部分点を出し、模範解答と見比べてもらう）

## 2. 前提

- **利用者**：本人のみ
- **端末**：PC とスマホ（レスポンシブ。入力は PC、復習はスマホ、のような使い分けを想定）
- **データ**：端末のブラウザ内（IndexedDB）に保存。JSON で書き出し・読み込みができる
- **端末間の同期**：スマホと PC で、解答記録と設定だけを同期する（ログインなし。同期キーを共有した端末どうし。§9.3）。フリーモードは端末ごと
- **オフライン**：PWA としてオフラインでも動く
- **複数ウィンドウでのリアルタイム同期（第一の設計思想）**：同じアプリを複数のウィンドウで開き、並べて使う。あるウィンドウで仕訳を入力すると、別のウィンドウの B/S・P/L・CF がその場で変わる（v1 の「別ウィンドウで開く」の考え方を引き継ぐ）
  - 各画面は URL で直接開けるようにする（別ウィンドウで開けるように）
  - 同じ端末のウィンドウ間の同期は BroadcastChannel で行う。状態を変えたウィンドウが変更を知らせ、ほかのウィンドウは保存先から読み直す
  - 解答記録・設定も同じ仕組みで同期する（あるウィンドウで解くと、別のウィンドウのレベルやストリークも更新される）
  - 実装：`src/data/sync.ts`。知らせるのは「どの種類のデータが変わったか」（`progress`／`ledger`）だけで、データそのものは送らない（保存先を正とする）
  - 保存と読み直しは 1 列に並べて順番に行う。読み直しがすでに始まっていても、保存し終わっていない変更は画面から消さない

## 3. コンセプト：明るいラボ

### 3.1 トーン
- 明るく、シンプルで、スタイリッシュ。余白が多く、情報がすっきり整理された「研究所」の雰囲気
- 参考イメージ：https://www.pkshatech.com/ai-saas/
- 論点ごとに「〇〇ラボ」を用意し、そこで問題を解いて検証していく
- ゲーム感は **採点の手応え・レベルと認定・ストリーク** の3本柱で出す。装飾は控えめにし、演出は要所に絞る
- 会計用語はそのまま使う（試験本番の用語と頭の中で結びつくように）

### 3.2 用語の対応
| v1 | v2 | 備考 |
|---|---|---|
| Stories / 預言 / クエスト | **問題**（1問）、**問題セット** | |
| Quest Clear | **採点** | 自己申告ではなく自動で判定 |
| Forge / Master Deck | **科目マスター** | 仕訳ラボ内の設定 |
| 精霊（Visual Types） | 廃止 | |
| Epoch Close | **決算振替** | |
| Scale | 廃止 | 天秤の演出はなくし、B/S はシンプルな表とグラフで表示する |
| Waterfall | **P/L の段階利益** | 売上高から当期純利益までをグラフで表示 |
| Matrix | **CF 計算書** | |
| Prism | **分析レーダー** | |
| — | **ラボ**（論点ごとの画面）、**レベル**、**認定テスト**、**ストリーク**、**今日のデイリー** | 新規 |

ラボの一覧：仕訳ラボ、分析ラボ、CF ラボ、CVP ラボ、投資ラボ（名前は仮）

### 3.3 ビジュアル
- **UI とクリエイティブは、Claude Design で作ったデザインシステム「Tessera」を適用する**
  - デザインシステム：https://claude.ai/artifact/1pte2p9RVUoVLuNDVyy3Ew（ルールは [`docs/design-system/README.md`](design-system/README.md) に写しを置く）
  - トークンの写し：[`docs/design-system/tessera-tokens.json`](design-system/tessera-tokens.json)。アプリでは `src/index.css` で CSS 変数と Tailwind のユーティリティに変換している
  - フォント：Satoshi は npm で配布されていないため、Tessera の代替指定どおり **Manrope**（英字）と **Noto Sans JP**（和文）をアプリに同梱する（オフラインでも表示が崩れないように）
  - 正解・不正解：Tessera の `correct`（ミントティール）と `incorrect`（ローズ）を、回答直後のフィードバックと成績表示だけに使う。必ず ○／× のマークと「正解」「不正解」の文字を添え、色だけで伝えない
  - アイコンは矢印だけ（Tessera のルール）。ナビやカードにはアイコンを付けず、文字で示す
  - 削除などの危険な操作の色は Tessera にないため、shadcn/ui の既定の赤を使う
  - 色、文字、余白、角丸、影、アイコン、コンポーネントの見た目はデザインシステムに従う
  - デザインシステムのトークンを Tailwind v4 のテーマ（CSS 変数）に取り込み、shadcn/ui の部品もそのトークンで見た目を合わせる
- このドキュメントでは、デザインシステムに依存しない決まりごとだけを定める
  - ライトテーマが基本（ダークモードは後回し）
  - 正解と不正解は、色だけでなくアイコンや形でも見分けられるようにする
  - 数字は等幅で表示して桁を揃え、**桁区切りと単位（千円・%・回）**を必ずつける

### 3.4 アニメーション方針
| 用途 | 手段 |
|---|---|
| ダイアログの開閉、ホバー、フォーカス | Tailwind のアニメーション用クラス |
| 正解の演出、レベルアップ・認定の演出、数値のカウントアップ、グラフの変化、画面遷移、並び替え | Motion |

- アニメーションにはこだわるが、スタイリッシュさを優先する。派手にするより、なめらかで気持ちいい動きを目指す
- 演出は**正解したとき・レベルアップや認定のとき・ストリークが伸びたとき**に集中させる
- OS の「視差効果を減らす」設定（`prefers-reduced-motion`）を尊重する
- 演出中も操作をブロックしない
- 動きの長さやイージングはデザイントークンとして定義し、全画面で揃える

### 3.5 効果音と BGM
- 効果音・BGM は音源ファイルを使わず、Web Audio でその場で合成する（`src/feedback/`）。ガラスの鈴のような澄んだ音で、明るいラボの世界観に合わせる
- 効果音：採点（全問正解・部分正解・不正解）、レベルアップ、ストリーク、認定（合格・不合格）、下のタブ。画面の演出と同じタイミングで鳴らす。間違えたときも責めるような音にはしない
- BGM：ゆっくりした和音とまばらな鈴の音を作り続けるアンビエント。はじめはオフ。画面を見ていない間は止める
- 振動（触覚フィードバック）は入れない。iPhone の Web アプリでは安定して振動させられないため（試したうえで外した）
- iPhone ではマナーモードを尊重し、ほかのアプリの音楽とも重ねられるようにする（`navigator.audioSession.type = 'ambient'`）
- 設定（オン・オフと音量）は端末ごとの好みなので、ほかの端末とは同期せず、ブラウザ（localStorage）に保存する

## 4. 学習のコアループ

```
ホームを開く
  → 「今日のデイリー」（例：3問）が出る
  → 問題を解く（ステップごとに入力）
  → すぐに採点：正誤、部分点、間違えた原因
  → XP と熟練度が更新される → 単元が定着すると、コースレベルが上がる
  → デイリー達成でストリーク +1
```

「今日のデイリー」は、ノルマと同じ数だけ選ぶ。選び方は学習の局面（マスター期間・維持期間・直前期）で変わる。マスター期間の基本は次の順（詳しくは [COURSE.md §9](COURSE.md)）。
1. 復習の期日が来た問題（前回全問正解できなかったものは RETRY、ほかは REVIEW と表示）
2. 導入期の型（新しい型に入ったら、3 回続けて正解するまで、数値を変えて同じ型を続ける。INTRO と表示）
3. まだ解いたことのない問題（次の単元の問題を先に）
4. しばらく解いていない問題

- **1 日の間は同じ問題が並ぶ**ように、今日より前の記録だけで選ぶ（復習の問題を解くと期日から外れるため、今日の記録まで使うとリストが途中で入れ替わってしまう）。今日の記録は「済み」の判定にだけ使う
- 問題の数値（シード）も日付から決めるので、何度開いても同じ問題になる
- デイリーは「今日のおすすめ」で、ストリークはデイリー以外の問題を解いても数える（間違いノートの解き直しなども含めて、その日に解いた問題数で判定する）
- デイリーから開いた問題では、「次の問題」が次のデイリーの問題に進む。全部解くと達成のバナーを出す

## 5. ゲーム要素の仕様

### 5.1 手応え：採点
- **ステップ採点**：1問をいくつかのステップに分けて、それぞれ採点する
  - 例（NPV）：① 毎年の税引後 CF → ② 各年の現在価値 → ③ NPV
  - 途中のステップが合っていれば部分点が入る
- **端数処理のルールは問題ごとに定義**する（例：「小数点第3位を四捨五入」「千円未満を切り捨て」）。採点ではそのルールを当てはめてから比較する
- **間違えた原因の推定**：問題テンプレートに「よくある誤答」の計算式を持たせる。ユーザーの答えがそのどれかと一致したら、原因を表示する
  - 例：「減価償却費の節税効果を足し忘れていない？」「期首と期末の平均を使っていない？」
- 正解したら気持ちいい演出、不正解なら模範解答と計算過程を表示する

### 5.2 上達が見える：単元の定着、コースレベル、認定

詳しい仕様と数値は [`docs/COURSE.md`](COURSE.md)（§4〜§9）。ここでは要点だけ書く。

- **問題ごとの記録**：解答するたびに、正誤・所要時間・解答日時を記録する。レベルや認定は保存せず、この記録から毎回計算する
- **学習コース**：Stage 1〜3 と 10 の単元。単元ごとに、未着手・学習中・定着・要復習 の状態を出す（定着には、正確さと「間を空けて解き直して正解」が要る）
- **コースレベル**：一度定着した単元の点で `Lv.1 → Lv.10`。要復習になっても下がらない。実力の目安はこれで見る
- **XP**：解いた量（積み上げた努力量）。ラボごとに出す。同じ型の周回には上限、間を空けた復習と難しい問題にはボーナス。レベルはない
- **熟練度**：ラボごとの、直近 10 問の得点率（新しい解答ほど重く）
- **認定**：`ブロンズ → シルバー → ゴールド`。Stage の修了テスト（単元をまたぐ混合セット）に合格したときだけもらえる。受けたときの制限時間・合格ラインを記録に残し、合否は記録から計算する。記述の小問は合否に使わない
- **復習スケジュール**：問題テンプレートごとに、次に出題する日を決める。間隔は学習の局面で変わる（マスター期間 1 → 3 → 7 → 14 → 30 日など）
- **記述の自己採点**：練習では、模範解答と見比べて 〇・△・✕ を付けると、キーワードによる目安の点を置き換える
- **間違いノート**：間違えた問題は自動で集まり、そこから復習できる

### 5.3 続けたくなる：ストリーク
- 1日のノルマ（初期値は3問。設定で変えられる）を達成するとストリークが +1
- **フリーズ**：7日続けると1つもらえる（最大2つ）。ノルマを達成できなかった日に自動で使われ、ストリークが途切れない
- 日付の切り替わり時刻は設定できる（例：午前4時）
- ストリークは保存せず、解答記録を最初の日からたどって毎回計算する。ノルマを変えると、過去の日も新しいノルマで判定し直す

## 6. 論点モジュール（v2 の範囲：0〜4）

事例Ⅳの本番では、財務諸表は最初から与えられることが多く、仕訳を切る場面は少ない。そのため**仕訳ラボは基礎トレーニング**、論点 1〜4 が**事例Ⅳの本番対策**という位置づけにする。

### 0. 仕訳ラボ（基礎）
- **演習モード**：取引の文章を読んで仕訳を入力 → 採点（科目と金額が合っているか。行の順番は問わない）
- **フリーモード**：v1 と同じく自由に仕訳を入力し、B/S・P/L・CF がリアルタイムに変わるのを見る。**仕訳の入力と財務諸表の表示を別々のウィンドウで開き、リアルタイムに同期させる**のが中心の使い方（§2）
- **科目マスター**：科目を作るときに**区分を必ず選ぶ**（§9.4）。名前からの推測は初期値を提案するだけ
- 決算振替、逆仕訳、取り消し（Undo）
- フリーモードの画面（各パネルは `/free/<パネル>?window=1` で、ナビを省いた別ウィンドウとして開ける）
  - 仕訳：入力と仕訳帳。貸借が合わない仕訳は記帳しない（v1 の「FORCE」はなくした）。取消（逆仕訳）、削除と「元に戻す」、決算振替
  - B/S：資産と負債・純資産の大きさを面積で見せるブロック図（v1 の天秤の代わり）と内訳
  - P/L：売上高から当期純利益までの段階利益を、バーで見せる
  - CF：期首の B/S がないため、現金預金が動いた仕訳ごとに、相手の科目の区分で営業・投資・財務に振り分ける（`src/domain/cashflow/byActivity.ts`）。合計は B/S の現金預金と必ず一致する
  - 科目マスター：区分は必ず選ぶ（名前からの推測は初期値だけ）。仕訳で使っている科目は削除できない
  - データは科目・仕訳を 1 件ずつ別のキーで保存し、複数ウィンドウが同時に書いても上書きし合わない

### 1. 経営分析
- 与えられた B/S・P/L（2期分、または同業他社との比較）から指標を計算する
- 優れている指標・劣っている指標を選ぶ → 短い記述（当面は自己採点）
- 扱う指標：
  - 収益性：売上高総利益率、売上高営業利益率、売上高経常利益率、売上高販管費比率
  - 効率性：総資本回転率、有形固定資産回転率、売上債権回転率、棚卸資産回転率
  - 安全性：流動比率、当座比率、自己資本比率、負債比率、固定比率、固定長期適合率、インタレスト・カバレッジ・レシオ
- 期末の値を使うか、期首と期末の平均を使うかは問題ごとに定義する
- 総資本は総資産と同じ値として扱う。棚卸資産回転率は「売上高 ÷ 棚卸資産」で計算する（v1 は売上原価を使っていた）
- 分析レーダーで、自社と比較対象を重ねて見られる

### 2. CF 計算書
- 2期分の B/S と当期の P/L から、**間接法の CF 計算書を穴埋め**で作る
  - 税引前当期純利益、減価償却費、引当金の増減、受取利息・配当金と支払利息の調整、売上債権・棚卸資産・仕入債務の増減、法人税等の支払額、投資 CF、財務 CF
- **v1 の教訓**：v1 は増減ではなく残高で計算していたため、2期分の B/S を前提にする

### 3. CVP 分析（損益分岐点）
- 変動費率、限界利益率、損益分岐点売上高、安全余裕率、目標利益を達成する売上高
- 費用の分解（高低点法など）、固定費削減や値下げのシナリオ
- グラフ：損益分岐点図（売上高線・総費用線が交わるところを動かして見られる）

### 4. 投資の意思決定（NPV）
- 毎年の税引後 CF ＝（売上高 − 現金支出費用 − 減価償却費）×（1 − 税率）＋ 減価償却費
- 取替投資の差額 CF、設備売却時の損益とその税効果、運転資本の増減
- NPV、回収期間（IRR は後回し）
- 複利現価係数・年金現価係数の表は問題の中で与える（本番と同じ形式）

### 論点 5 以降（将来）
意思決定会計（セグメント別損益、差額原価）、企業価値・リスク管理（為替予約、オプション）、記述問題の強化。

## 7. 問題集の設計

### 7.1 基本の考え方：テンプレート＋計算エンジン
```
問題テンプレート（文章と構造）
  ＋ 数値パラメータ（範囲の中でランダムに生成）
  → 正解は計算エンジンが算出する（テスト済みのドメインロジック）
```
- 同じ論点を**数字を変えて何度でも**解ける
- **正解は必ずエンジンが出す**。文章を AI で作っても、計算ミスが正解に混ざらない
- 数値の組み合わせが不自然にならないよう、テンプレートにパラメータの制約を書ける（例：変動費率は 40〜80%、NPV の符号を指定する）

### 7.2 問題データの形（イメージ）
```ts
type ProblemTemplate = {
  id: string;                 // 例: "cvp.bep.basic-01"
  topic: 'journal' | 'analysis' | 'cf' | 'cvp' | 'npv';
  title: string;
  difficulty: 1 | 2 | 3;
  source: {
    kind: 'original' | 'past-exam' | 'ai-generated';
    note?: string;            // 例: "令和5年度 第2問を参考"
    publishable: boolean;     // 公開版に含めてよいか
  };
  params: ParamSpec;          // 数値パラメータの範囲と制約
  body: (p: Params) => RichText;          // 問題文
  steps: {
    id: string;
    prompt: string;
    answer: (p: Params) => number | JournalEntry[] | string;
    rounding?: RoundingRule;  // 端数処理
    unit?: '千円' | '円' | '%' | '回';
    commonMistakes?: { answer: (p: Params) => number; hint: string }[];
  }[];
  explanation: (p: Params) => RichText;   // 解説と計算過程
};
```
- 実装では Zod でスキーマを定義し、読み込むときに検証する
- 問題は `src/problems/<topic>/` に置き、`npm run validate:problems` で全テンプレートをランダムな数値で繰り返し実行して、エラーや不自然な値が出ないか確認する

### 7.3 出典と公開時の扱い
| 出典 | 使い方 | 公開版 |
|---|---|---|
| オリジナル | 自作、またはエンジンから生成 | 含める |
| AI 生成（NotebookLM など） | **文章だけ**使い、数値と正解はエンジンが出す。人の目で確認してから追加する | 確認済みのものは含める |
| 過去問 | 本人の学習用。構造を参考にしたテンプレートにする | **含めない**（著作権は中小企業診断協会にある） |

- 過去問をもとにした問題は `src/problems/_private/` に分けて置き、公開用のビルドから外せるようにする

### 7.4 NotebookLM で問題を作る流れ
1. 教材や論点のメモを NotebookLM に読み込ませる
2. §7.2 の形に合わせた「問題文とステップの下書き」を出力させる（プロンプトはリポジトリの `docs/prompts/` に置く）
3. 下書きをテンプレートに変換し、正解の計算はエンジンの関数につなぐ
4. `validate:problems` を通してから追加する

### 9.2 依存の向き
```
features → engine / progress → domain

```

### 9.3 保存と同期
- 画面や状態管理は保存先を直接触らず、`data/` の repository 経由で読み書きする
- すべてのレコードに `id`（UUID）、`createdAt`、`updatedAt` を持たせる。削除は論理削除（`deletedAt`）にする
- 書き出し・読み込み：全データを JSON でバックアップ、復元できる（読み込み時に Zod で検証する）

#### 端末間の同期（解答記録と設定だけ）
- **ログインなし**：最初の端末で「同期キー」（160 ビットのランダムな 32 文字）を作り、ほかの端末に QR コードか手入力で渡す。キーを知っている端末どうしでデータがまとまる
  - QR コードの URL は `/settings#sync=キー`。キーは `#` の後ろに置き、サーバーやログに残らないようにする。読み取ったらすぐ URL から消す
  - キーはパスワードと同じ扱い（知っている人は記録を読み書きできる）。画面にもそう書く
- **サーバー**：Cloudflare Worker の `POST /api/sync`（`Authorization: Bearer キー`）。キーの SHA-256 で Durable Object（SQLite 版）を 1 つ選び、そこに記録を置く。キーそのものは保存しない
- **1 回の同期**（`src/sync/client.ts`）：前回送ったあとに変わった記録と今の設定を送り、サーバーの通し番号（cursor）より後に変わった記録を受け取って取り込む
- **まとめ方**（`src/sync/merge.ts`。端末とサーバーで同じ関数）：
  - 解答記録は id ごと。同じ id なら `updatedAt` が新しい方。同じ時刻なら削除の印がある方
  - 削除は `deletedAt` を付けて残す（すべて消去・バックアップの読み込みで置き換えたときも、消えた記録に印を付けて、ほかの端末にも消したことを伝える）
  - 設定は `updatedAt` が新しい方
- **きっかけ**：起動時、この端末で記録や設定が変わったとき（3 秒まとめる）、画面に戻ったとき、オンラインに戻ったとき、5 分ごと
- フリーモード（仕訳ラボの科目と仕訳）は同期しない。バックアップの書き出し・読み込みで移す

### 9.4 v1 のバグから決めたルール
| v1 で起きたこと | v2 のルール |
|---|---|
| 科目名のキーワードだけで区分を推測し、「売上原価」が売上、「役員報酬」が売上と判定された | **科目の区分は作成時に明示的に選ぶ**。推測は初期値の提案だけにする。区分は「大区分（資産・負債・純資産・収益・費用）＋ 小区分（流動資産、売上原価、販管費、営業外収益 など）」の2階層 |
| 貸倒引当金が CF で二重計上された | CF は B/S の増減から計算する。論点ごとにテストケースを用意する |
| 進行中のクエストのボタンを押すと、仕訳が確認なしで消えた | データを消す操作には、**確認ダイアログか Undo のどちらかを必ずつける** |
| 進行中のクエストを削除しても、HUD が残った | 状態は正規化して1か所で持ち、派生する値は計算で出す（二重に持たない） |
| 科目を削除しても、それを使う仕訳が残った | 使用中の科目は削除できないようにする（アーカイブにする） |
| クリア演出が一度も動かなかった | 演出のきっかけになるイベントもテストの対象にする |
